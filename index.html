1. 공통 설계 원칙과 전체 구성

무엇에 대한 장인가 세 주제의 공통 설계 원칙과 계층형 전체 구성. 2~4장 그림은 이 구성의 일부를 확대한 것.

설계 원칙 10가지

원칙이유
LLM은 제안, 확정은 코드와 사람계산·권한·되돌릴 수 없는 행동은 결과가 항상 같아야 하고 책임 주체가 필요
정해진 흐름이 뼈대, 자율성은 일부에만재현·감사·비용 예측. 자율성은 대화와 탐색(무엇을 더 찾을지)에만, 반복 상한
원본은 고치지 않고, 결과에는 버전원본이 있어야 다시 처리, 결과마다 버전이 있어야 과거 판단 설명 (예: OCR v1 결과만 v2로 재처리)
버전·권한은 검색이 아니라 조건으로개정 전후 문장은 거의 같아 유사도로 구분 불가. 권한 밖 문서는 아예 후보에서 제외
근거는 인용 단위로 남기고 원문 대조설명 의무, 지어낸 근거 차단
같은 요청 두 번 = 결과 하나(멱등성)재시도·타임아웃·큐 중복 전달은 반드시 일어남
즉시 응답은 짧게, 오래 걸리는 일은 큐로피크 흡수. 화면 연결과 작업의 수명을 분리
상태의 기준은 서버 한 곳화면·채널·기기는 보여 주고 입력만 받음. 이어 하기·충돌 감지가 가능
모든 LLM 호출은 게이트웨이 경유민감정보 가리기, 사용 한도, 모델 교체, 호출 기록을 한곳에서
변경은 평가를 통과해야 배포모델·프롬프트·규칙·색인 변경 시 골든셋 회귀 평가, 단계적 배포, 되돌리기

2. AI 기반 데이터 파이프라인과 근거 데이터

무엇에 대한 장인가 AI가 쓸 데이터를 원천(문서·이미지·업무 DB·처리 이력)에서 가져와 수집 → 가공 → 검증 → 저장 → 제공으로 준비하는 과정, 그리고 AI의 답·판단이 기대는 근거(출처·버전·위치가 붙은 데이터)를 남겨 설명·재현하는 방법. 핵심 원본은 고치지 않고, AI 결과는 검증을 통과해야 저장하며, 버전은 검색이 아니라 조건으로 맞춘다.

단계 구성

요소하는 일왜기술 예
규정 문서 (예: 약관·매뉴얼 PDF) · 등록될 때 배치
① 배치 수집문서 등록 이벤트로 원본을 가져와 보관자주 안 바뀌고 저장 전 확인 필요Airflow
② 문서 파싱레이아웃 분석 → 단 순서로 추출 → 구조(조·절) 단위로 나눔, 표 별도, 버전 메타데이터구조가 깨지면 검색·인용이 깨짐PyMuPDF, pdfplumber, LLM 보조
③ 구조 검사원문 대비 조항 수·표 개수·누락률, 버전 중복정답 없이 틀린 것 찾기검증 규칙
④ 근거 DB·색인DB에 문서·버전·조각 저장 → 임베딩 → 색인DB가 근거의 원본, 색인은 다시 만드는 사본PostgreSQL, OpenSearch
⑤ 검색 API버전·권한 조건을 먼저 걸고 하이브리드 검색RAG 근거 제공사내 API
서류 이미지 (예: 영수증·신청서) · 들어오는 즉시
⑥ 업로드·큐원본 보관 후 대기열에 넣고 즉시 접수 응답피크 흡수, 사용자는 기다리지 않음REST API, Kafka
⑦ 서류 판독이미지 품질 확인 → OCR·멀티모달 LLM으로 값 추출사람 입력 대체사내 OCR, 멀티모달 LLM
⑧ 교차 검증합계 = 총액, 두 방법 값 일치, 서류 간 대조오독 검출규칙 코드
⑨⑩ 저장·입력값 + 파일·페이지·위치 + 모델 버전 저장 → 업무 처리의 입력값어디서 무엇으로 읽었는지 추적PostgreSQL
업무 DB (예: 계약·주문) · 처리 이력 (예: 심사·상담 결과) · 같은 기간계에서 수집
⑪ 변경분 복제바뀐 행만 복사 → 스테이징(단기)원천 부하 최소, 원본은 원천이 관리Debezium(CDC), 일 배치
⑫ 형식 맞추기목표 스키마로 변환항상 같은 결과 → AI 쓰지 않음SQL, dbt
⑬ 대조 검사건수·합계를 원본과 비교원본이 정확하므로 직접 비교 가능검증 규칙
⑭⑮ 업무 데이터·조회조회용 사본, 에이전트 조회 도구. 판단 직전에는 원천 직접 조회숫자·상태는 검색이 아니라 조회, 복제 시차 보완데이터 마트, 도구 API·MCP
⑯ 분류·연결자유 메모 → 사유 코드(LLM), 당시 서류·문서 버전과 연결평가에 쓰려면 정형화와 당시 맥락 필요소형 LLM
⑰ 사람 검수분류 확인, 의견이 갈리면 2인 합의, 유형 편중 확인정답 데이터는 사람이 확정검수 화면
⑱⑲ 평가 데이터·실행정답·사람 수정 이력(비식별) → 변경 시 회귀 평가품질 측정, 나빠지면 배포 차단평가 파이프라인
공통
원본 보관원본 파일은 영구(고치지 않음), 정형 사본은 단기재처리·감사의 기준S3 호환(MinIO)
통과 판정기준값 비교 → 저장 / 격리(그 건만 사람) / 차단(적재 중단)AI 결과는 검증 후에만 저장판정 규칙
실행·이력·보안·지표재시도, 데이터 이력(원천·실행·버전), 수집 시 민감정보 분류·대체값, 누락률·분포 변화 알림추적·보안·이상 감지를 한 번에Airflow, OpenLineage, Vault·KMS, Grafana
형태는 수집·가공 방법을, 쓰임새는 검증 기준과 저장·제공 방식을 정한다. 업무 DB와 처리 이력은 형태가 같아 수집이 같고, 쓰임새(사실 조회 / 정답 데이터)가 달라 가공부터 갈라진다. 숫자·상태처럼 정확해야 하는 값은 RAG가 아니라 조회로.

원천마다 (형태, 쓰임새)를 정해 칸을 채운다. 다섯 단계 열과 공통 띠는 원천이 하나여도 유지. 같은 PDF라도 사내 규정은 "근거", 검토할 계약서는 "처리 입력". 검증 칸에는 그 업무만의 규칙을 하나 넣는다(예: 세금계산서 공급가액 + 세액 = 합계). 정답·피드백 줄은 요구에 없어도 거의 항상 추가.

근거 데이터 모델

인용 단위와 버전 맞추기

  • 인용 단위 = 구조 단위(조·항·절). 사람이 읽고 설명·감사·개정 비교하는 단위. 고정 길이 조각은 부적합
  • 적재: (대상, 시행일)마다 버전 ID 발급, 이전 버전 종료일을 닫음(덮어쓰기 금지). 모든 조각에 버전 ID·시행일·종료일·조항 ID
  • 조회: 기준일(예: 가입일·신청일)로 SQL 조회 → 버전 조건을 먼저 걸고 그 안에서만 검색. 0건이면 오류(조건 없는 검색 금지)
  • 내용이 같은 조각은 본문 고유값으로 임베딩 재사용

저장소 4종

  • 객체 저장소: 원본 파일(고치지 않음)
  • 관계형 DB: 근거·관계의 기준
  • 검색 색인: 다시 만들 수 있는 사본(모델 교체·손상 시 재생성)
  • 판단 기록: 추가만 가능, 감사·재현용
  • 추출값에는 파일·페이지·위치·모델 버전 → 화면에서 원본 위치 강조, 같은 모델로 읽은 건 역추적

정답 없이 검사하는 4가지 신호

  • 반드시 성립하는 관계 (합계 = 총액, 번호 연속)
  • 쉽게 셀 수 있는 것과 대조 (목차 조항 수, 페이지 수)
  • 실패 방식이 다른 두 방법 (OCR ↔ 멀티모달)
  • 다른 출처 (마스터 데이터, 코드 목록)
  • 한계: 틀림은 증명, 맞음은 보장 못 함 → 표본 감사로 놓친 비율 측정

기준값과 미달 시 조치

  • 기준값은 업무 목표에서 역산(예: 오처리율 0.5% → 금액 오독률은 그보다 훨씬 낮게), 과거 데이터로 실측, 처음엔 엄격
  • 차단: 적재 중단 (누락률 초과, 버전 충돌)
  • 격리: 그 건만 사람에게 (값 불일치)
  • 알림: 적재하되 경고 (분포 변화 → 새 양식 신호)
  • 원본을 완벽히 읽어도 조각내기·매핑·적재 중 누락·중복이 생기므로 검증은 필요

재처리·근거 재현·개인정보

재처리와 버전 교체

  • 모든 결과에 파서·모델·실행 버전, 중간 결과 보관 → 실패한 단계부터 재실행
  • 멱등 키 = 내용 고유값 + 처리 버전
  • 교체: 새 버전 병행 생성 → 골든셋 비교 → 검색 별칭 전환 → 이상 시 별칭 되돌리기
  • 임베딩만 바뀌면 색인 단계만 재실행
  • 대량 재처리는 할인 배치 API, 실시간과 LLM 한도 분리

개인정보와 근거 보존

  • 식별정보는 대체값(토큰), 실제 값은 토큰 금고에만
  • 삭제 요청 → 금고의 연결만 삭제. 기록은 누구 것인지 모르는 상태로 남아 근거 유지
  • 법정 보관 대상은 근거·기간 표시 후 제외, 만료 시 자동 파기
  • 백업·색인까지 전파, 임베딩·로그에 식별정보 넣지 않음, 삭제 로그

3. AI Agent 워크플로우와 LLM·RAG

무엇에 대한 장인가 AI가 업무를 처리하는 실행 구조. 정해진 워크플로우가 단계를 지휘하고, LLM은 단계 안에서 판단을 제안하며, RAG로 근거를 찾아 인용한다. 핵심 자율성은 대화·탐색에만, 쓰기 도구는 검증·승인 후에만, 모든 LLM 호출은 게이트웨이로, 계산은 코드로.

생성구조화 출력(결과·근거 ID·인용문·사유), "근거 없음" 허용지어내기 방지, 사람에게 넘길 길

대상 문서가 짧으면 검색 대신 해당 장 전체 + 프롬프트 캐싱도 가능 (누락 없음, 토큰 비용↑). 문서 분량으로 선택.

도구, 실패 대응, 보안

도구 설계

  • 읽기·쓰기 분리. 쓰기는 LLM이 직접 못 부름
  • 도구 하나는 좁게, 입출력 형식 명확, 오류는 LLM이 이해할 문장
  • 사용자 식별자는 서버가 세션에서 넣음 (LLM이 넘기지 않음 → 남의 데이터 조회 불가)
  • 쓰기 안전장치: 멱등 키, 1회용 승인 토큰(승인 내용에 묶임), 서버에서 한도 재검증, 맨 마지막 한 번만

실패·장시간 처리

  • 시간 제한, 읽기만 자동 재시도, 연속 실패 → 사람
  • 반복 상한·토큰 예산, 같은 호출 반복 시 중단
  • 며칠 대기: 상태 저장 후 종료 → 이벤트로 재개, 재개 시 원천 재조회, 기한 지나면 종결
  • 폴백: 보조 모델 → 규칙만 적용 → 사람 대기열 (품질 기준은 낮추지 않음)

숨긴 지시문(프롬프트 인젝션)

  • 입력 문서는 데이터로 구분해 전달 (이것만으로는 부족)
  • 구조로 막기: 읽는 단계엔 도구 권한 없음, 정해진 형식 값만 다음 단계로, 쓰기는 LLM 권한 밖
  • 지시문 발견 시 의심 건으로 사람에게

민감정보·비용

  • LLM 보내기 전·로그에서 가림, 망분리 허용 구간 모델, 학습 미사용 조건
  • 작은 모델로 분류 → 필요할 때만 큰 모델, 프롬프트 캐싱, 조회 결과 짧은 캐시
  • 판단 결과는 캐시하지 않음(매번 기록), 배치 API, 실시간·배치 한도 분리

RAG 품질 진단

틀린 답 표본을 순서대로 확인: 정답 조각이 ① 색인에 있나 → ② 조건 범위 안에 있나 → ③ 검색 상위 k에 있나 → ④ 리랭크 후 남았나 → ⑤ 받고도 틀렸나 → ⑥ 질문·정답이 명확한가. 정답 조각을 직접 주고 답하게 해 생성 단계의 상한을 잰다. 원인별 건수가 많은 것부터, 한 번에 하나씩 바꾸고 전후 비교.
원인개선지표
검색 안 됨구조 단위 조각, 상위 제목, BM25 추가, 질의 재작성재현율@k (정답이 상위 k에 든 비율)
순위 낮음리랭커, 가져오는 개수 조정MRR (정답이 얼마나 위에)
받고도 틀림인용 강제, 확인 순서 지정(지급 → 예외 → 한도), 정의 조항 동봉, 상위 모델, 계산은 코드충실도(근거 기반 정도), 정답 일치
표 내용 누락표 구조 파싱, 행 단위 문장화표 질의 정답률
없는데 답함"근거 없음" 허용, 검색 점수 낮으면 보류모를 때 모른다 비율

평가 데이터: 실제 질의 300~500개, 유형별 층화, 답 없는 질문 포함, 전문가 검수. LLM 평가자는 사람 평가와 일치율을 확인한 뒤 사용. 색인 갱신: 덮어쓰지 않고 새 버전 추가 → 검수 → 검증용 색인 → 회귀 평가 → 별칭 전환. 시행일 전에 미리 색인해도 조건이 노출을 막음.

구조 선택과 MCP

에이전트 하나 + 도구 다수역할별 멀티 에이전트워크플로우가 지휘 (권장)
장점단순, 추적 쉬움컨텍스트 분리, 병렬역할 분리의 장점 + 재현·단계별 평가
단점도구가 많으면 잘못 고름전달 중 정보 손실, 비용, 오류 전파, 디버깅유연성 낮음
맞는 곳좁고 순차적인 일독립적으로 병렬 처리할 하위 작업규제·업무 처리

MCP 이점과 위험

  • 이점: 연동 표준화, 도구 재사용, 도구 팀·에이전트 팀 분리
  • 권한 과다 → 사용자 권한 위임, 최소 권한
  • 인증 → 표준 인증, 받은 토큰 재전달 금지
  • 도구 과다 → 단계별로 필요한 것만 노출
  • 믿을 수 없는 서버·결과 속 지시 → 승인 목록, 결과는 데이터로 취급

도입 순서와 관측

  • 조회 도구 → 담당자 보조 도구 → 쓰기는 승인 절차 뒤
  • 외부 공개 서버 사용 금지, 모든 호출 게이트웨이 기록
  • 요청 번호 = 추적 번호. 호출마다 입력·출력·버전·토큰·지연·오류
  • 실패 건 재현용 입력 보관, 사람이 뒤집은 건과 추적 연결

4. AI Agent 기반 동적 UI 연동

무엇에 대한 장인가 에이전트가 대화 중에 필요한 화면 요소(달력·검색·요약 카드 등)를 띄우고, 사용자의 조작을 다시 받아 처리하는 화면 ↔ 서버 연동 구조. 핵심 에이전트는 명세만 보내고 화면은 등록된 요소만 그리며, 조작은 문장이 아닌 구조화 이벤트로 돌아오고, 상태의 기준은 서버 하나다.

블록 구성

요소하는 일왜기술 예
① 스트림 수신서버 이벤트로 화면 갱신, 끊기면 마지막 번호부터실시간 표시, 재연결EventSource(SSE)
②③ 렌더러·요소 목록명세의 이름을 등록된 화면 요소에 대응해 그림, 요소별 입력 형식테스트된 요소만 사용 → 보안·일관성·접근성React, 디자인 시스템
④ 이벤트 송신조작을 {요소 ID, 행동, 값, 상태 버전}으로 전송값을 문장으로 바꿔 LLM이 다시 해석하지 않게HTTP POST
⑤ 스트림 중계이벤트 종류별 전송, 번호 부여끊긴 지점부터 이어 받기Node.js·Spring BFF
⑥ 명세 검증스키마·지원 요소 확인. 실패 시 오류를 돌려 1회 재생성 → 기본 입력 양식잘못된 명세가 화면에 나가지 않음JSON Schema
⑦ 인증·세션로그인 확인, 화면이 그릴 수 있는 요소·버전 협상예전 버전 앱과 호환OIDC(Keycloak)
⑧ 입력 재검증형식·범위·권한 확인, 민감값은 가린 값·참조 번호로화면에서 온 값은 믿지 않음BFF
⑨ 대화 에이전트의도 파악, 필요한 화면 요소를 도구 호출로 요청에이전트는 화면을 직접 그리지 않음LLM 도구 호출
⑩ 상태 관리진행 중 입력의 단일 기준, 항목 단위 자동 저장, 버전 번호기기·채널을 바꿔도 이어서, 동시 수정 충돌 감지Redis, PostgreSQL
⑪⑫ 작업·알림오래 걸리는 처리(예: 서류 판독)를 화면과 분리, 완료 시 푸시연결이 끊겨도 작업 계속, 떠나도 돌아오게Kafka, FCM·APNs

대화와 화면 요소 나누기

대화로화면 요소로
의도 파악, 자유 서술(예: 사고 경위), 예외·질문 응대, 결과 설명형식이 정해진 값(달력, 검색 자동완성, 목록 선택), 선택지, 확인·수정(요약 카드), 진행 단계, 파일 올리기
이미 아는 것은 묻지 않는다(조회해 선택지로). 문서에서 읽을 수 있는 것은 묻지 않는다(먼저 받아 자동 채움). 대화와 화면 요소가 같은 상태를 본다(어느 쪽으로 고쳐도 같은 값이 바뀜). 예) 항목 10개를 대화로만 받으면 20턴 이상 → 화면 요소로 6~8턴.

방식장단점

호환·보안·오류·장시간 작업

호환과 보안

  • 세션 시작 시 지원 요소·버전 협상 → 에이전트의 UI 도구 목록을 맞춤
  • 모르는 요소는 대체 문장을 보여 주고 대화로 입력
  • 명세 변경은 추가만, 깨지는 변경은 버전 올림
  • LLM이 만든 HTML·스크립트는 그리지 않음, 글자는 이스케이프, 링크는 허용 도메인만
  • 제출은 서버 상태 조건을 만족할 때만

오류와 결과 표시

  • 명세 오류 → 1회 재생성 → 기본 양식. 에이전트 장애 → 일반 입력 양식(대화 없이도 완료)
  • 판단·금액은 흘려보내지 않음: 확정값만 카드로 한 번에, 설명은 그 뒤 스트리밍
  • 스트림 중단 → "응답 중단" 표시 + 다시 시도(중복 접수 없게)
  • 재심으로 바뀌면 덮어쓰지 않고 이력과 사유 표시

오래 걸리는 작업과 복귀

  • 즉시 접수 표시 + 진행 단계, 기다리는 동안 다음 입력 진행, 10초 넘으면 "나가도 됩니다"
  • 작업 수명 ≠ 연결 수명: 작업은 큐·워커, 화면은 진행 이벤트만
  • 복귀 시 대화 재생이 아니라 상태로 화면 복원("이어서 하기")
  • 계정 기준 서버 상태 → 다른 기기에서 이어서, 버전 번호로 충돌 감지, 보관 기간(예: 7일)

접근성·성능·지표

  • 큰 글자·대비, 터치 44px 이상, 한 화면 한 가지 일, 시간 제한 없음, 음성 입력
  • 스트리밍 글은 문장 단위로 낭독기에, 새 요소에 초점 이동, 키보드 조작
  • 글자 조각 모아서 갱신, 긴 목록 가상화, 요소 자리 미리 확보
  • 지표: 완료율, 건당 턴 수, 단계별 이탈, 복귀 후 완료율, 명세 실패율. 연령·채널별로 나눠 A/B 비교

사람 승인 화면과 결과 전달

승인 카드와 반영

  • 보여 줄 것: 하려는 일(한 문장), 근거(원문·계산 내역·추출값 위치), 영향(금액·대상·되돌릴 수 있는지), 선택(승인 / 거절+사유 / 수정)
  • 결과는 구조화 이벤트 → 서버 검증 → 상태 갱신
  • 승인 시 1회용 토큰(승인 내용에 묶임) → 쓰기 도구는 토큰 + 멱등 키 필요
  • 수정 후에는 재검증 → 카드 다시 표시, 승인 기록 보관
  • 승인 버튼은 응답이 끝난 뒤 활성. 승인 대기 중 처리는 상태 저장 후 멈춤

결과 전달

  • 순서: 결론 → 이유 한 문장 → 계산 내역 → 근거 원문 → 다음 할 일
  • 근거는 기록에서 가져옴(그 자리에서 지어내지 않음), 숫자·조항 번호는 기록 값 그대로
  • 불리한 결과는 사람이 확정한 뒤 통지, 이의 제기 방법·기한 명시
  • 상담사 연결 시 요약·근거·쟁점·대화 요약을 카드로 넘겨 같은 설명 반복 없게

5. 전체 흐름, 위험, 단계적 도입

무엇에 대한 장인가 세 주제를 하나의 서비스로 묶었을 때의 처리 흐름, 가장 큰 위험과 대응, 단계적 도입과 변경 배포, 영역별 지표.

전체 흐름 (1장 전체 구성 그림 기준)

#흐름담당
1사용자 요청 → 의도 파악, 이미 아는 정보는 조회해 선택지로대화 에이전트
2문서·이미지 업로드 → 원본 보관 → 판독 작업을 큐에, 진행 상황 표시BFF, 큐, 판독
3읽은 값이 요약 카드에 자동 채움 → 사용자 확인·수정 → 제출, 즉시 접수 번호화면, 상태 관리
4업무 데이터 조회로 기준 버전 확정 → 조건 안에서 근거 검색(예외 조항 포함)워크플로우, RAG
5LLM이 판단 제안(인용 포함), 계산은 규칙 엔진, 검증(값·인용·규칙·이상치)워크플로우, 규칙 엔진
6저위험이고 모든 검증 통과 → 자동 처리, 아니면 사람 승인워크플로우, 담당자
7기간계 반영(멱등 키) → 알림 → 결과 카드(결론·계산·근거)연계 어댑터, 알림

가장 큰 위험 세 가지

위험왜대응
잘못된 자동 처리직접 손실, 건수가 많아 누적다단계 검증, 금액·건수 상한, 표본 감사, 기준값 실측 보정, 사람이 뒤집는 비율 알림
근거·버전 오류판단 근거 자체가 틀림, 설명 의무 위반버전은 코드로, 예외 조항 필수 포함, 인용 원문 대조, 근거 없으면 사람
민감정보 유출·숨긴 지시문민감 데이터와 외부 입력을 함께 다룸가림·토큰화, 허용 구간 모델, 읽는 단계 권한 없음, 쓰기는 LLM 밖, 등록 요소만 그림

LLM 장애는 일반 입력 양식과 사람 대기열로 전환하면 서비스가 멈추지 않아 순위가 낮다.

단계적 도입과 변경 배포

단계내용다음 단계 조건 (예)
1. 사람 보조AI는 추출·제안만, 모든 건을 사람이 확정, 평가 데이터 축적추출 정확도 98%, 제안과 사람 확정 일치 90%
2. 제한적 자동화저위험·소액·단순 건만 자동, 새 화면은 일부 사용자에 A/B표본 오류율 목표 이하, 완료율 상승
3. 확대범위·채널 확대자동 처리율 목표, 민원율 유지
되돌림 조건을 미리 정한다(예: 주간 오류율 초과 → 자동 처리 상한을 이전 단계로). 모델·프롬프트·규칙·색인 변경은 유형별 골든셋 회귀 → 섀도 실행(결과 미반영) → 카나리(5 → 25 → 100%) → 이상 시 자동 되돌림. 모든 판단에 사용 버전을 기록.
